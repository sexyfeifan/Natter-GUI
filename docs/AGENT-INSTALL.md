# 使用 AI Agent 安装 Natter GUI

适用于能执行终端命令、使用 SSH 的 AI Agent。以下指令授权 Agent 在指定设备上完成安装、开机启动和指定服务配置；它需要实际的设备访问权限，只有聊天能力的助手不能代替执行。运行环境的权限与审批要求仍然适用。

## 填写设备与服务信息

只需要提供你知道的信息，Agent 应先检测可以从设备取得的环境信息。

| 信息 | 填写方式 |
|---|---|
| 目标设备 | 本机 / 远程设备 / 请先询问；远程需要设备 IP 或主机名、SSH 端口和账号，密码或密钥按需提供 |
| 安装方式 | 自动 / 原生 systemd / Docker；不指定时由 Agent 根据设备选择 |
| 服务列表 | 名称、目标局域网 IPv4、目标端口、协议、绑定端口；没有服务也可先安装面板 |
| 网络出口 | 是否存在旁路由、期望的主路由 IPv4；网卡可由 Agent 检测 |
| 现有安装 | 已有 Natter 或 Natter GUI 的位置；不知道时先检查 |
| 管理密码 | 新安装默认 `admin`；升级保留原密码，明确要求后才重置 |

## 远程安装时主动询问连接信息

“本机”指 Agent 实际执行命令的机器。没有明确安装位置时，Agent 应先确认目标，不能默认把用户想安装的香橙派 / NAS 当成 Agent 本机。

选择远程设备后，Agent 在连接前集中询问缺少的信息，示例提示：

```text
要安装到远程设备，我需要先通过 SSH 连接。请补充尚未提供的连接信息：
设备 IP 或主机名：
SSH 端口：默认22，如有不同请说明。
SSH 账号：
认证方式：已有可用密钥，或在私有会话中提供 SSH 密码。
如果已配置可用密钥，不需要再提供密码。
```

已有信息直接沿用，不重复索要。未提供账号时不能默认 `root`；也不能把面板默认密码 `admin` 当成 SSH 密码。连接信息缺失或认证失败时先等待用户补充，不在 Agent 本机代替安装。目标是局域网 IP 而 Agent 没有到该网络的路由时，说明当前无法访问，并询问可用的连接路径；不能直接断言设备离线。

## 服务信息示例

示例服务信息如下，地址和端口都是示例，需换成你的真实环境：

```text
Emby：192.168.1.100:8096，TCP，香橙派绑定端口 34569。
Plex：192.168.1.100:32400，TCP，香橙派绑定端口 34570。
qBittorrent：192.168.1.100:64046，TCP 和 UDP，香橙派绑定端口 64046。
```

qBittorrent 应填写 BT 监听端口，不是 Web 管理端口。未指定绑定端口的新服务可自动分配；迁移已有入口时应保留原绑定端口。

## 完整自然语言安装指令

复制下面的整段内容给 Agent，替换方括号中的信息。不要把设备密码、私钥或应用令牌写入公共仓库。

```text
请帮我在指定设备上实际安装、配置并验收 Natter GUI，完成工作，不要只输出方案或让我逐条复制安装命令。

项目仓库：https://github.com/sexyfeifan/Natter-GUI
目标设备：[本机 / 远程设备 / 请先询问我]
远程连接：[设备 IP 或主机名、SSH 端口、SSH 账号；可以留空，由你在连接前提示我补充]
认证方式：[使用已有 SSH 密钥，或在需要时提示我在私有会话中提供 SSH 密码]
安装方式：[自动 / 原生 systemd / Docker]
需要映射的服务：[每项服务的名称、目标局域网 IPv4、目标端口、TCP/UDP/两者、绑定端口；也可以写“先只安装面板”]
网络情况：[默认网关、是否有旁路由、主路由 IPv4；未知信息先检测]
现有安装：[已有 Natter / Natter GUI 的位置，或“请先检测”]
管理员密码：[新安装使用 admin；已有安装保留当前密码；需要重置时明确写“重置为 admin”]

请先读取仓库 README.md、docs/DEPLOYMENT.md、docs/STATUS.md 和 docs/UPDATES.md，并核对实际安装脚本、命令参数和 API。按以下流程执行。

0. 确认安装目标并连接。如果我没有说明本机还是远程设备，先询问安装位置；“本机”必须是你实际执行命令的机器。远程安装时，连接前集中提示我补充缺少的设备 IP 或主机名、SSH 端口、SSH 账号和密码或密钥。SSH 端口未指定时默认22，账号不能默认 root；有可用密钥时无需索要密码。已提供的信息直接使用，不重复询问。SSH 密码只用于指定设备的认证，不回显到日志、不写入源码、提交记录或公共文档。信息不足或认证失败时，等待我补充必要信息再继续；不能转而在你本机安装。无法访问目标局域网时，说明缺少网络路径，并询问可用连接方式。确认连接到正确设备后再检查环境和执行安装。

1. 检查环境。确认目标设备的操作系统、CPU 架构、Python 版本、systemd、Docker/Compose、可用权限、网卡、IPv4、默认路由和端口占用。检查已有 GUI、Natter 进程、systemd 实例、容器及配置位置，辨别本次是全新安装、升级还是迁移。只在缺少必要信息时向我询问；能从设备取得的信息请自行检查。发现工作目录有未提交改动时保留它们，使用独立目录取得新版本。

2. 准备备份。改动前建立带时间戳的备份，记录旧代码版本、配置与状态目录、服务启动状态、绑定端口、已知公网入口、相关 systemd 单元/override、容器镜像和卷、已有专用路由。配置中可能含认证数据，备份应限制访问。给出本次部署可执行的回退方法，再开始切换；不要删除旧状态、旧代码或旧服务配置。

3. 获取并校验代码。优先使用本仓库最新正式 GUI Release 的源码安装包或镜像，并记录所选版本；如果没有合适的正式发布，使用 main 的明确提交并记录 SHA。源码安装包下载后核对对应 SHA256SUMS，在独立目录解压，再运行 python3 scripts/sync_upstream.py --verify。GUI 已自带锁定的 Natter 核心，不需要另外安装第二份 Natter，也不要直接修改 vendor/natter 或单独把核心替换成上游 master。

4. 选择安装方式。Linux、systemd 和 Python 3.11+ 均满足时，优先按项目原生方式执行 sudo ./scripts/install.sh；仅使用发行版支持的来源安装确实缺少的依赖。NAS 或已有 Linux Docker 环境可使用仓库 compose.yaml：在独立项目目录中先 docker compose pull，再 docker compose up -d --no-build。使用 Linux host 网络、持久化状态卷，确认镜像支持目标架构。版本固定时在 Compose override 中使用已发布的准确标签或摘要。已有安装优先保持原安装方式、项目名和状态位置，避免启动第二个面板。遇到9080端口冲突时先查清占用者，使用该安装方式支持的配置调整，不能直接终止无关服务。如果现有环境不支持这两种方式，明确说明缺少的条件。

5. 配置正确出口。检查是否存在旁路由、代理或多层 NAT。只有我指定直走主路由或已确认需要专用出口时，才在原生安装中使用 sudo ./scripts/install.sh --gateway 实际主路由IPv4 --interface 实际网卡。验证网关可达、属于网卡子网，检查策略优先级13457和路由表34568是否冲突，保留已有专用路由设置。该路由只匹配 natter-gui 专用账户，不修改系统默认网关，也不接管设备上其他代理/VPN。Docker 使用宿主机既有出口，不能声称原生安装的账户路由自动适用于容器。检查 UPnP 是否可用；缺少路由管理权限时，给出具体需要处理的网络条件，不凭空宣称已经修改主路由。

6. 登录并配置服务。新安装使用默认密码 admin，不添加密码长度或复杂度要求，不强制首次修改。升级已有 GUI 时保留原密码，只有我明确要求才按项目支持的方式重置。不要为了重置密码删除状态目录。面板管理入口不作为需要公开映射的业务服务。使用实际面板或项目已有 API 配置指定服务；通过 API 操作时保留会话 cookie，并携带登录返回的 CSRF token，不绕过认证。每项服务先以停用状态保存，核对目标 IPv4、目标端口、绑定地址、绑定端口、协议、UPnP 和保活设置。TCP 与 UDP 分别管理；目标应用需要认证时保留其认证，不为了让测试通过而关闭登录验证。

7. 无损迁移或升级。已有 GUI 升级使用原状态目录/卷，保留服务配置和密码。已有手工 Natter 实例迁移时，先备份并建立对应的停用 GUI 服务，再仅停止匹配这些端口的旧实例，取消它们的重复开机启动，随后启用 GUI 服务。保留原目标、端口和协议；不迁移未指定的其他实例，不修改 NAS 数据、媒体库或下载任务。若公网入口变化，明确告诉我哪些客户端地址需要调整。无损指配置和数据保留；切换期间可能短暂中断连接，不保证正在播放或下载的连接不断开。失败时先停止新映射，再按备份恢复旧服务，避免同一端口出现两个监听者。

8. 验证运行与连通。检查 /healthz、实际登录、左下角 GUI/核心版本、服务配置和日志。检查目标 LAN 端口、香橙派绑定端口、实际核心进程和公网映射；TCP/UDP 服务要分别验证。正确解释原版 OPEN/CLOSED/UNKNOWN、NatterCheck 的 NA/FAIL 和类型编号，不把“运行中”“获取到映射”“检测程序完成”当作外网可达。内网访问公网地址失败可能是 NAT 回环问题，不据此直接判定外网失败。socket 转发会改变目标软件看到的来源 IP，核对应用原有的访问控制是否仍符合预期。

9. 验证外网与性能。能使用独立外网测试端时，从外网访问当前入口，确认应用页面、登录或连接；有权限和条件时实际播放验证。没有真正外网环境时，请让我用关闭 Wi-Fi 的手机测试，明确列出地址并标记待验证。Plex 的网页可打开不能证明客户端播放已直连，需要核对客户端是否连接新入口及是否仍显示间接连接。BT 监听端口的 TCP 与 UDP 可达性分别判断，按需核对应用向 Tracker 宣告的端口。不要把 Natter 描述为运营商限速解除工具：播放速度受家里上传带宽、外网下载带宽、代理路径、转码和码率设置影响；BT 还受节点与种子影响。若需要比较速度，使用同一外网、同一任务和相同应用设置，注明 Mbps 与 MB/s 的区别；没有对照测量就报告“未验证提速”。

10. 验证维护和交付。确认原生 systemd 或容器重启策略有效，在备份和端口切换完成后检查一次对应管理服务重启后的恢复，不为验收直接重启整台设备。说明仓库自动同步上游不等于设备自动升级，面板“检查上游版本”也不会在线替换核心。最终给我实际面板 URL、管理员登录方式、GUI 与核心版本、安装方式、各服务的当前入口、验证结果、待验证项、备份位置、对应部署的升级/回退命令。只报告实际完成的动作；遇到权限或连接障碍时明确说明已经完成的部分和缺少的条件。
```

## 验收结果应当明确

Agent 完成后应给出以下结果，未知项保持未知：

- 面板可以访问并登录，GUI 与核心版本能够查看。
- 指定服务的配置正确；旧实例与新实例不争用端口。
- 每项服务的进程、映射、原版检查与外网实测分别报告。
- 相关服务重启后恢复；已有配置、密码和业务数据得到保留。
- 备份位置、升级与回退方法符合实际安装方式。
- 没有独立外网测试或速度对照时，明确写出“外网待验证”或“提速未验证”。

详细命令以 [部署与迁移说明](DEPLOYMENT.md) 为准，状态解释以 [状态判定标准](STATUS.md) 为准，版本同步和设备升级以 [更新机制](UPDATES.md) 为准。
